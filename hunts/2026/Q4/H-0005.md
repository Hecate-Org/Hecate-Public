### Hypothesis Statement

Adversaries execute PowerShell command lines containing web download methods (`Net.WebClient.DownloadString`, `Invoke-WebRequest`, `Invoke-RestMethod`) combined with `Invoke-Expression` to download and execute secondary payloads directly in memory on Windows endpoints.

### Justification

PowerShell web download cradles are one of the most prevalent and effective living-off-the-land techniques observed across modern intrusions. By fetching remote scripts over HTTP/HTTPS directly into process memory and evaluating them via `Invoke-Expression` (`IEX`), adversaries bypass file-based antivirus inspection and leave minimal disk forensics. Proactive hunting across process creation command lines and host network egress identifies active staging and initial loader execution before secondary persistence or ransomware encryption occurs.

### Executive Summary

PowerShell web download cradles are extensively exploited to accomplish in-memory payload execution and file staging without writing binaries to disk. The deployed multi-SIEM detection suite provides comprehensive layered visibility across process creation command lines (detecting `DownloadString`, `Invoke-WebRequest`, `Invoke-RestMethod`, and `IEX`), window-hiding obfuscation flags, and direct process network egress sessions.

### Recommended Response & Remediation
1. Isolate the affected endpoint if unknown external IP connections or interactive shells are spawned by `powershell.exe`.
2. Inspect Windows PowerShell ScriptBlock Logging (Event ID 4104) to review the de-obfuscated script body that was passed to `Invoke-Expression`.
3. Enable PowerShell Constrained Language Mode (CLM) and application control policies (WDAC) to prevent unconstrained in-memory reflection.
