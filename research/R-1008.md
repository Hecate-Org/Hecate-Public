## 1. System Research: How It Works

### Summary
WordPress Core performs full-package upgrades by downloading update files to a predictable, web-accessible staging directory, validating the package, and then moving files into production. During this process, the upgrade mechanism creates temporary files in known paths that remain accessible via HTTP/HTTPS until the upgrade completes, creating a narrow window between file creation (time-of-check) and final deployment (time-of-use).

### Key Findings
- WordPress Core upgrade process writes temporary staging files to predictable web-accessible paths during full-package updates, generating HTTP requests to download core update packages and filesystem activity in staging directories.
- The upgrade mechanism exhibits a TOCTOU race condition where files are validated after being written to accessible staging paths but before being moved to their final location, creating exploitable timing windows observable through web server access logs showing requests to staging directories.
- Successful exploitation during the upgrade window results in unauthenticated remote code execution, generating anomalous PHP process execution, unexpected web requests to staging paths (e.g., /wp-content/upgrade/ or similar predictable directories), and potential outbound connections from the web server process.
- Affected WordPress Core versions 4.7.0 through 7.1.3 generate network traffic to WordPress update servers (api.wordpress.org) during upgrade checks and package downloads, with the vulnerability window opening only during active core upgrade operations.
- Version 7.1.4 and later implement mitigations that alter the staging path behavior or access controls, observable through changes in filesystem permissions, directory naming patterns, or HTTP 403/404 responses to previously accessible staging paths.

## 2. Adversary Tradecraft: Attack Techniques

### Summary
Adversaries exploit CVE-2026-119977, a Time-of-check Time-of-use (TOCTOU) race condition in WordPress Core versions 4.7.0 through 7.1.3, to achieve unauthenticated remote code execution during the upgrade process. The vulnerability allows attackers to exploit predictable, web-accessible staging paths used during full-package core upgrades to execute arbitrary code on the server. CISA confirmed active exploitation in the wild as of November 2026.

### Key Findings
- The vulnerability affects WordPress Core versions 4.7.0 through 7.1.3 and has a CVSS score of 8.1 (High severity) with the vector CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H, indicating network-based exploitation with high complexity but no authentication required
- Attackers exploit a race condition during the WordPress upgrade window by targeting predictable staging paths that remain temporarily web-accessible during full-package core updates
- The attack requires no authentication (PR:N) and enables complete compromise with high impact to confidentiality, integrity, and availability, allowing arbitrary code execution on the target server
- CISA added CVE-2026-119977 to the Known Exploited Vulnerabilities (KEV) catalog on November 3, 2026, with a patching deadline of November 6, 2026 for federal agencies, confirming active in-the-wild exploitation
- EPSS scoring indicates 1.20% exploit probability (68.4th percentile) as of November 9, 2026, while VulnCheck and AlienVault OTX confirm active exploitation with 16 threat intelligence pulses tracking the vulnerability
- The vulnerability requires attackers to win a race condition (AC:H - high attack complexity) by accessing staging files between the time-of-check and time-of-use during the upgrade process

## 5. Research Synthesis

### Executive Summary
CVE-2026-119977 is a TOCTOU race condition in WordPress Core 4.7.0-7.1.3 enabling unauthenticated RCE during upgrade operations via predictable web-accessible staging paths. Detection requires correlating rapid concurrent HTTP requests to upgrade endpoints with file creation in staging directories (/wp-content/upgrade/*) and subsequent process execution from web server contexts. CISA KEV listing confirms active exploitation as of November 2026, requiring hunt focus on upgrade-window timing attacks and staging path abuse.

### Recommended Hypothesis
> Adversaries use rapid concurrent HTTP requests to predictable WordPress staging paths during core upgrade windows to win TOCTOU race conditions and achieve unauthenticated remote code execution on WordPress servers running versions 4.7.0-7.1.3

### Gaps Identified
- Web server access logs may lack sub-second timestamp precision or correlation with filesystem events needed to identify millisecond-scale race condition attempts against staging directories during upgrade windows
- Process execution telemetry may not capture the parent-child relationship between web server workers and spawned processes originating from staging directory file execution, particularly if process lineage breaks at FastCGI/PHP-FPM boundaries
- File creation/modification events in /wp-content/upgrade/* staging paths may not be collected or retained with sufficient fidelity to distinguish legitimate upgrade operations from injected malicious files during the narrow exploitation window

### Key Findings
- Hypothesis: Adversaries use rapid concurrent HTTP requests to predictable WordPress staging paths during core upgrade windows to win TOCTOU race conditions and achieve unauthenticated remote code execution on WordPress servers running versions 4.7.0-7.1.3
- Gap: Web server access logs may lack sub-second timestamp precision or correlation with filesystem events needed to identify millisecond-scale race condition attempts against staging directories during upgrade windows
- Gap: Process execution telemetry may not capture the parent-child relationship between web server workers and spawned processes originating from staging directory file execution, particularly if process lineage breaks at FastCGI/PHP-FPM boundaries
- Gap: File creation/modification events in /wp-content/upgrade/* staging paths may not be collected or retained with sufficient fidelity to distinguish legitimate upgrade operations from injected malicious files during the narrow exploitation window
- Focus: Correlate web server access logs showing concurrent requests to /wp-admin/update-core.php or /wp-content/upgrade/* paths (within sub-second intervals) with file creation events in staging directories and subsequent PHP process execution from those paths
- Focus: Hunt for unauthenticated HTTP requests (lacking valid wp-admin session cookies) to WordPress staging paths that precede or coincide with file writes to /wp-content/upgrade/* followed by web server process spawning unexpected child processes (bash, sh, curl, wget)
- Focus: Identify WordPress installations running affected versions 4.7.0-7.1.3 with evidence of recent upgrade activity (api.wordpress.org connections, update-core.php access) and examine surrounding time windows for anomalous staging directory access patterns or process execution from web contexts
