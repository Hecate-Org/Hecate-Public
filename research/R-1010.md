## 1. System Research: How It Works

### Summary
CVE-2026-109618 and CVE-2026-109619 are critical remote code execution vulnerabilities in the PHP scripting language itself (not a separate tool called 'php2shell'). CVE-2026-109618 exploits PHP's out-of-memory handling during request processing, where cleanup code incorrectly trusts partially-initialized internal data structures. CVE-2026-109619 is a use-after-free vulnerability where session upload progress tracking state from one request persists and points to freed memory that can be manipulated by subsequent requests.

### Key Findings
- Exploitation is triggered via standard multipart POST requests to PHP endpoints when session.upload_progress.enabled=1 (default configuration), allowing unauthenticated attackers to execute arbitrary code without requiring special application logic vulnerabilities
- The vulnerability affects PHP versions before 8.5.12, 8.4.27, 8.3.36, and 8.2.35, as well as all older unsupported branches including PHP 5, representing a massive attack surface across web infrastructure
- VulnCheck KEV confirms active in-the-wild exploitation, and FIRST EPSS assigns 100% exploit probability (100th percentile), indicating widespread automated exploitation is occurring or imminent
- Public proof-of-concept tools include Python-based checkers (checker.py) that accept target URLs and can operate in local or authorized testing modes, generating JSON and Markdown reports, with example targets including /ping.php endpoints
- The vulnerability cluster (CVE-2026-109618, CVE-2026-109619, CVE-2026-115560) involves memory management flaws including ASLR boundary issues and default memory configuration weaknesses that persist across request boundaries in PHP's session handling

## 2. Adversary Tradecraft: Attack Techniques

### Summary
CVE-2026-109618 and CVE-2026-109619 (collectively known as PHP2Shell) are critical memory-safety vulnerabilities in PHP core functionality, rated CVSS 9.2, that enable unauthenticated remote code execution. The vulnerabilities exploit heap use-after-free conditions during failed memory allocations, where PHP's longjmp() handling abandons request context unsafely, allowing attackers to execute code as the PHP web worker or read process memory. Emergency patches were released October 21, 2026 for PHP versions 8.5.12, 8.4.27, 8.3.36, and 8.2.35, affecting all PHP web-serving configurations including PHP-FPM, Apache mod_php, php-cgi, FrankenPHP, and LiteSpeed.

### Key Findings
- CVE-2026-109618 and CVE-2026-109619 have EPSS scores of 100% (100th percentile) indicating critical exploit probability, and VulnCheck KEV confirms both are actively exploited in-the-wild targeting PHP installations
- The attack vector (T1190 - Exploit Public-Facing Application) targets PHP's handling of out-of-memory conditions and use-after-free scenarios, allowing remote code execution without authentication
- A public PoC repository (JoshRob297/php2shell-research) provides checker tooling (checker.py) with command-line examples targeting endpoints like /ping.php, demonstrating vulnerability verification capabilities
- Multiple security vendors have deployed detection coverage including Datadog Security, Elastic, Trellix (network and endpoint), and Cymulate, mapping detections to MITRE techniques T1190 and T1505.003
- The vulnerability affects all PHP web-serving configurations and requires immediate patching to fixed versions; the risk spans any PHP installation serving web requests globally

## 5. Research Synthesis

### Executive Summary
CVE-2026-109618/109619 (PHP2Shell) are critical RCE vulnerabilities in PHP core (versions <8.5.12/8.4.27/8.3.36/8.2.35) exploiting use-after-free conditions during out-of-memory handling via standard multipart POST requests to any PHP endpoint with session.upload_progress.enabled=1 (default). VulnCheck KEV confirms active in-the-wild exploitation with EPSS 100% (100th percentile), and public PoCs (JoshRob297/php2shell-research) demonstrate exploitation via HTTP requests without requiring application-specific vulnerabilities. Detection requires correlating HTTP request characteristics (multipart uploads, session upload progress headers) with web worker process spawning shells/interpreters, though encrypted HTTPS traffic and normal PHP-FPM process forking patterns complicate behavioral detection.

### Recommended Hypothesis
> Adversaries use crafted multipart POST requests with session upload progress parameters to trigger use-after-free conditions in PHP core, achieving unauthenticated remote code execution on PHP-enabled web servers (versions <8.5.12/8.4.27/8.3.36/8.2.35) to establish initial access via T1190

### Gaps Identified
- TLS encryption prevents inspection of multipart POST body content and session.upload_progress parameters in HTTP request payloads without SSL/TLS interception, limiting ability to detect exploitation attempts based on request structure
- PHP-FPM and php-cgi architectures legitimately spawn child processes for request handling, making behavioral detection of web worker processes spawning interpreters noisy without baselining normal process trees per deployment model (mod_php vs FPM vs CGI vs LiteSpeed)
- Web server access logs may not capture POST body parameters, session headers, or memory-related error conditions that distinguish exploitation attempts from legitimate failed uploads, requiring application-layer logging or WAF telemetry not universally deployed

### Key Findings
- Hypothesis: Adversaries use crafted multipart POST requests with session upload progress parameters to trigger use-after-free conditions in PHP core, achieving unauthenticated remote code execution on PHP-enabled web servers (versions <8.5.12/8.4.27/8.3.36/8.2.35) to establish initial access via T1190
- Gap: TLS encryption prevents inspection of multipart POST body content and session.upload_progress parameters in HTTP request payloads without SSL/TLS interception, limiting ability to detect exploitation attempts based on request structure
- Gap: PHP-FPM and php-cgi architectures legitimately spawn child processes for request handling, making behavioral detection of web worker processes spawning interpreters noisy without baselining normal process trees per deployment model (mod_php vs FPM vs CGI vs LiteSpeed)
- Gap: Web server access logs may not capture POST body parameters, session headers, or memory-related error conditions that distinguish exploitation attempts from legitimate failed uploads, requiring application-layer logging or WAF telemetry not universally deployed
- Focus: Correlate HTTP requests with Content-Type: multipart/form-data AND PHP-Session-Upload-Progress or session.upload_progress headers to PHP endpoints (process.parent_process.name IN [httpd, nginx, php-fpm, w3wp.exe, lsphp]) followed within 60 seconds by child process creation (process.name IN [sh, bash, cmd.exe, powershell.exe, python, perl, nc, curl, wget]) to detect post-exploitation command execution
- Focus: Hunt for PHP worker processes (php, php-fpm, php-cgi) establishing outbound network connections (destination.port NOT IN [80, 443, 53] AND network.direction=outbound) that deviate from expected database/cache backend communication patterns, indicating reverse shells or C2 beaconing post-RCE
- Focus: Identify vulnerable PHP versions in the estate by correlating web server process telemetry (process.executable.version_info OR package inventory) against affected version ranges (<8.5.12, <8.4.27, <8.3.36, <8.2.35, all 5.x/7.x branches) to scope exposure, then prioritize monitoring hosts running unpatched PHP with public-facing listeners
