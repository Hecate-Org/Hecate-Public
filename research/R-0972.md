# SocGholish / FakeUpdates: behavioral intrusion hunt

Prepared 2026-10-29 UTC. Analyst synthesis of five public primary reports. Each observation belongs to its cited report and time window. The reports have no explicit TLP marking; do not invent one. Windows endpoints are the detection scope. No report below establishes a Washington state election compromise. Election workstations are a proposed defensive application, not an observed target in this dossier.

## Evidence ledger

### S1 — Trend Micro / TrendAI, 14 March 2025
SocGholish's Intrusion Techniques Facilitate Distribution of RansomHub Ransomware
https://www.trendaisecurity.com/en-us/resources-insights/trendai-security-blog/socgholishs-intrusion-techniques-facilitate-distribution-of-rans

Observed: compromised sites and Keitaro redirects delivered fake-update JavaScript. Users launched the loader through wscript.exe. It profiled Windows hosts and accepted remote tasks. Operators enumerated domain trusts with nltest and performed reconnaissance using systeminfo, ipconfig, account/group and share enumeration. Task output was staged temporarily and returned to C2. The investigation documented copying browser credential stores, certutil.exe reading SAM/SECURITY/SYSTEM from Volume Shadow Copies, a Python backdoor persisted through a scheduled task, and SSH remote forwarding using -R. These later actions represent the reported intrusion, not a required outcome of every loader infection. This report explicitly maps JavaScript execution (T1059.007), user execution (T1204.002), domain trusts (T1482), scheduled tasks (T1053.005), browser credentials (T1555.003), SAM access (T1003.002), and protocol tunneling (T1572).

### S2 — Red Canary, current Threat Detection Report, observations from 2025
SocGholish
https://redcanary.com/threat-detection-report/threats/socgholish/

Observed: both direct JavaScript downloads and ZIP-wrapped payloads, including Unicode lookalikes in update filenames. Detection opportunities include browser-associated wscript.exe execution followed by external connections, and nltest.exe arguments /domain_trusts or /all_trusts. Initial reconnaissance can run inside the script without separate child processes, making script-content telemetry valuable. Reported follow-on payloads differed: MintsLoader with subsequent malware in one cluster, Python backdoors and ransomware-precursor reconnaissance in another. Vendor testing references include Atomic Red Team T1059.007 test 2, T1033 test 6 and T1482 test 2. A browser parent is useful evidence where observed; Explorer or archive-tool ancestry must also remain discoverable in this hunt.

### S3 — Darktrace, 1 May 2025, investigations beginning January 2025
SocGholish: From loader and C2 activity to RansomHub deployment
https://www.darktrace.com/blog/socgholish-from-loader-and-c2-activity-to-ransomhub-deployment

Observed in different cases: external WebDAV authentication attempts using Microsoft-WebDAV-MiniRedir/10.0.19045, and Thumbs.scf copied to internal SMB shares with IconFile pointing to an external UNC destination. These support investigation of forced authentication (T1187), not an assertion that credentials were successfully stolen. Follow-on traffic included changing destination ports such as 2308, 2311 and 2313 to the same address. The report distinguishes compromised delivery sites, TDS infrastructure, loader C2 and Python-backdoor infrastructure. Treat those roles separately. A failed WebDAV session is neither proof of safety nor proof of successful credential extraction. Ports and filenames are pivots; they require process and user correlation before attribution.

### S4 — Huntress, 17 July 2024, observations from 4 July 2024
Fake Browser Updates Lead to BOINC Volunteer Computing Software
https://www.huntress.com/blog/fake-browser-updates-lead-to-boinc-volunteer-computing-software

Observed fake-update activity branched into AsyncRAT and unauthorized BOINC installations. PowerShell delivered files into AppData, unpacked and renamed BOINC executables, and installed scheduled tasks. Example names included System_Health_Service_790926033 and executables impersonating trustedinstaller.exe or SecurityHealthService.exe. A registry value HKCU\Software\Microsoft\ExpirienceHost containing 1 was an infection marker; it was NOT itself a Run-key persistence mechanism. BOINC is legitimate software and its presence alone does not establish compromise. Huntress noted attribution overlap and reported no subsequent malicious BOINC tasks observed at publication. Keep this as a conditional historical branch rather than mandatory SocGholish behavior. Do not manufacture a universal UpdateCheck task or infer a registry Run key from the marker.

### S5 — Infoblox, 18 June 2026
Hot Take: Operation Endgame VS SocGholish
https://www.infoblox.com/blog/threat-intelligence/hot-take-operation-endgame-vs-socgholish/

Observed distribution involves traffic acquisition, filtering, fake updates and an on-device JScript stager. Tier-one delivery/fingerprinting hosts and tier-two stager C2 are different roles; domain shadowing lets malicious subdomains inherit a legitimate parent's apparent reputation. Endpoint suitability influences later payloads. The June 2026 disruption affected servers, domains and compromised WordPress sites. DNS exposure counts do not measure successful endpoint compromise. Historical 2024/2025 infrastructure must not be labeled active in October 2026 without new validation. Hunt newly seen subdomains and script-associated traffic through enterprise telemetry, not broad blocks against all parent-domain users.

## Analyst hunt specification (proposed checks, not additional incident facts)

Hypothesis to test: user-launched browser-update JavaScript on managed Windows endpoints produces a connected sequence of script execution, external traffic and discovery; a subset progresses to scheduled-task persistence, credential-store access or tunneling. Determine whether our telemetry contains that sequence and which branch is supported. Shared behaviors alone cannot uniquely identify SocGholish; corroborate content, provenance and sequence.

Build five explicit prongs:
1. Delivery and execution: browser/download history and Mark-of-the-Web, ZIP or direct .js creation, wscript.exe/cscript.exe execution from Downloads, Temp or AppData. Cover explorer.exe/archive ancestry as well as a browser parent. Preserve original Unicode filenames; normalized names are an analyst pivot only. Treat .js plus script host as a candidate, not a confirmed compromise.
2. Discovery and egress: correlate candidate process ancestry with outbound network activity, script-load/AMSI content and nltest trust enumeration. Use process GUID/entity ID, device ID and user SID. Domain membership and discovery are context, not proof of ransomware.
3. Persistence: task creation/modification whose action executes script, Python or a renamed binary from a user-writable directory; inspect task XML, trigger, principal, action and signatures. The BOINC branch is optional and must retain S4's uncertainty. Registry marker must not be called persistence.
4. Credential access and lateral exposure: browser-store copying, certutil reads from shadow copies, suspicious SCF creation on shares, external WebDAV/NTLM attempts. Differentiate attempt, access, collection and proven exfiltration. Follow matched devices/users into authentication and share telemetry.
5. Follow-on access and tunneling: unexpected Python and ssh.exe -R after the candidate chain, including task ancestry and unusual egress. Do not claim every fake update installs these tools or that any ransomware payload is inevitable.

Telemetry prerequisites: EDR/Sysmon process creation (Event 1) or Security 4688 with command lines; EDR process-attributed network or Sysmon 3; DNS/Sysmon 22 and proxy URL/method/user-agent logs; file events/Sysmon 11 with optional file content; PowerShell 4104 where enabled; task telemetry Security 4698/4702 and TaskScheduler Operational logs; authentication 4624/4625 and share access 5140/5145 where collected. These are required collection options, not a claim that every source documented each event ID. No SIEM field mapping is assumed available.

Generate real standalone Sigma rules and translated Splunk SPL, Sentinel KQL and Elastic queries where conversion supports each logsource. Prefer observable behavior selections over historical IOC lists. Include source references, ATT&CK tags, required fields and false-positive explanations per rule. Cover at least script execution, nltest trust discovery, suspicious task actions, credential-access behavior, SCF/WebDAV and SSH forwarding if supported; explicitly list unsupported logsources or rejected rules. A generic process-only rule cannot by itself express a cross-source correlation: supply separate candidate rules and a clearly labeled correlation plan.

Analyst correlation windows: first inspect 15 minutes around candidate execution, widen to 24 hours for persistence/follow-on activity and to seven days for an initial retrospective sweep. These are tunable hunt parameters. Keep joins bounded by device and process ancestry; NAT/shared public IP is insufficient. Use a 30-day baseline if retained to identify sanctioned scripts, deployment tasks, BOINC projects, SSH tunnels, browser automation and support tools. Exclude verified approved hashes/signatures and specific known tasks; do not broadly exclude signed Windows binaries or all administrative users.

Disposition: confirmed malicious sequence needs script/download provenance and corroborating execution or follow-on evidence. Isolated discovery commands, legitimate BOINC, public DNS lookups and failed network attempts remain investigative leads. A clean result is inconclusive when execution, script, task or network telemetry is missing. Measure observable prong coverage, candidate counts, corroborated chains and uncovered behavior. Include an attack-flow diagram, triage steps, scoping pivots, confidence levels and handoff evidence requirements.

Validation: distinguish static query validation, synthetic source-artifact replay, Atomic Red Team simulation and real CALDERA execution. The current environment uses a mock SIEM query backend; never report live SIEM detection as proven. Do not launch live BAS as part of CTI generation. Use positive and benign replay cases where supported, record per-rule gaps and platform limitations, and accurately report any rejected rule and promotion-policy blocker. Do not relax gates to make this hunt appear complete.
